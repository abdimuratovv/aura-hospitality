## What this project is

AURA is an AI-driven hospitality finance platform: night audit automation, fraud detection, revenue-leakage recovery, employee risk scoring — for hotel groups. The full target architecture (from a diagram the user shared) has 6 layers:

1. **Hotel systems (data sources)** — OPERA/Fidelio (PMS), MICROS POS, SAP/1C ERP, CCTV/Access, Bank/Payroll, Wi-Fi/Firewall logs.
2. **Data Connectors** — pyodbc, REST API, file parsers, real-time streams.
3. **Data storage layer** — PostgreSQL (transactional), ClickHouse (analytics/OLAP), Redis (cache/queue), Celery (background tasks).
4. **AI Engine** (PyTorch, XGBoost, Scikit-learn, LangChain) — Night Audit AI, Finance AI/Revenue Leakage, Fraud Detection AI, Cybersecurity AI, HR AI/Behavioral.
5. **Alert Engine** — Telegram, Email, SMS, in-app notifications.
6. **Executive Dashboard** — React, Next.js, Tailwind CSS. Screens: GM Command center, Fraud alerts, Cyber incidents, Employee risk heatmap.

## Backend

**Database:** Neon (hosted Postgres, free tier), region ap-southeast-1. Connection string lives in `aura-next/.env.local` (gitignored) as `DATABASE_URL`. Also has `SESSION_SECRET` (random 32-byte string for signing session JWTs). Template at `aura-next/.env.example`. **Neon free tier auto-suspends when idle** — the first Prisma command after a period of inactivity commonly fails once with `P1001`/`P1017` and succeeds on immediate retry while the compute wakes up; this is expected, not a real connectivity bug.

**ORM:** Prisma 7. **Very new major version, breaking changes from what most training data knows:**
- `schema.prisma`'s `datasource` block has no `url` — connection config for the CLI lives in `aura-next/prisma.config.ts` (a `defineConfig({ datasource: { url: env('DATABASE_URL') } })` call, loaded via `dotenv` reading `.env.local` explicitly since Prisma CLI doesn't auto-read `.env.local`).
- The Prisma Client at runtime requires an explicit **driver adapter** (`@prisma/adapter-neon`, since we're on Neon) passed to `new PrismaClient({ adapter })` — see `src/lib/db.js`.
- **After every `schema.prisma` change you must run `npx prisma generate` separately** — `migrate dev` does not reliably regenerate the client in this setup; forgetting this produces `Unknown argument` / `Cannot read properties of undefined` errors on fields/models that clearly exist in the schema.
- The seed command moved from `package.json`'s `"prisma"` key into `prisma.config.ts` under `migrations.seed` (currently `"node prisma/seed.mjs"`).
- Adding a required (non-null, no-default) column to a table that already has rows will make `prisma migrate dev` refuse to run. Fix by using `--create-only` to generate the SQL file, hand-editing it to add the column nullable + `UPDATE ... SET` backfill + `ALTER ... SET NOT NULL`, then `prisma migrate dev` again to apply it. Don't reach for `migrate reset` to dodge this — it drops all data and is blocked by the auto-mode permission classifier as destructive; the create-only + backfill path is the correct non-destructive fix, used for `Property.shortName` in migration `20260725074452_add_screen_models`.
- Don't assume old Prisma docs/patterns apply generally; check https://www.prisma.io/docs if something seems off.

**Seeding:** `npx prisma db seed` runs `prisma/seed.mjs`, which is idempotent (deletes-then-recreates each table's rows, `upsert`s Users/Properties by unique key) so it's safe to re-run. Seeds: 2 dev users — `e.reyes@meridianhotels.com` (CFO, portfolio-wide access, all 6 properties) and `r.chandra@meridianhotels.com` (GM, scoped to Bayside only) — both password `aura-secure-2026` (dev-only credential), 6 properties (codes GM/BS/OT/HB/SM/RV, each with a `name` and a shorter `shortName` used in table/card display), 7 `UserProperty` access grants (6 for the CFO + 1 for the GM), 32 transactions, 6 employees, 6 fraud cases, 30 leakage categories (5 per property, added 2026-08-05 — was 5 portfolio-wide rows before), 7 alerts (each now tagged with a `propertyId`), 6 night audit runs — one per property, each with its own 6 checklist items and its own completion story (Bayside/Harbor fully closed, Grand Meridian/Summit have open discrepancies, matching the pre-existing `discrepancyAmount` figures), 6 report definitions, 3 insights, 42 property risk scores (6 properties × 7 days), 1 dashboard snapshot, 72 weekly financials rows (12 weeks × 6 properties, added 2026-08-05 — was 12 portfolio-wide rows before). Add to this file rather than duplicating formatting logic per-screen. Response-shaping helpers that are reused across a list route and its `[id]` PATCH route (`serializeFraudCase`, `serializeAlert`, `serializeNightAuditRun`) live in `src/lib/serializers.js` — don't export them from a `route.js` file itself, Next.js route handlers only permit HTTP-verb exports (`GET`/`POST`/etc.) plus a few route-config constants.

**Property-level RBAC:** `src/lib/access.js`'s `getAccessiblePropertyIds(userId)` looks up the caller's `UserProperty` rows and returns the property IDs they can see; every property-scoped route filters its Prisma query with `where: { propertyId: { in: propertyIds } } }`. An empty array correctly yields zero rows (Prisma's `{ in: [] }`), so a user with no grants sees nothing rather than everything — access is opt-in. `resolvePropertyIds(accessibleIds, requestedId)` (same file) narrows that set to a single `?propertyId=` query param *only* if it's inside the accessible set, otherwise silently falls back to the full accessible set — the request param is a display filter, never a way to escalate access. As of 2026-08-05 this covers every model with a `propertyId`: Transaction/Employee/FraudCase/PropertyRiskScore/Alert/NightAuditRun/LeakageCategory/WeeklyFinancials reads, the FraudCase and Alert status-update writes, the NightAuditRun checklist-item write, and the cross-entity search route. Routes with multiple accessible properties in scope (`leakage`, and `dashboard`'s `weeklyFinancials`/`revenueLeakage`) group/sum rows across those properties to reconstruct a portfolio view rather than just filtering — see those routes above. It does not (and structurally cannot yet) cover `Insight`/`ReportDefinition`/`DashboardSnapshot`, which have no `propertyId` field.

## AI Engine (`ai-service/`)

**Wave 3 kicked off 2026-08-05**: a separate Python service (FastAPI), not in-Node — resolves the connector-architecture question left open in Wave 2. Reasoning: Wave 3's ML libraries (PyTorch/XGBoost/LangChain) can't run in the Node runtime, and PMS/POS connector tooling (`pyodbc`) is far stronger in Python, so standing up one Python service now — that later grows to house both AI models and connectors — avoids building connectors in Node first and re-doing that boundary when the AI layer arrives. Connects to the *same* Neon Postgres DB as `aura-next` via a plain `psycopg2` connection to the same `DATABASE_URL` value (a standard `postgresql://` connection string, not a Neon-proprietary/HTTP-only scheme — a normal Python driver reaches it directly, no special adapter needed like Node's `@prisma/adapter-neon`). Prisma (in `aura-next/`) stays the schema/migration owner; `ai-service` only does CRUD against tables Prisma already created and never runs its own migrations.

**First slice: rule-based Fraud Detection AI.** `ai-service/app/rules.py` has 4 pure, IO-free functions that scan `Transaction` rows for patterns and produce candidate `FraudCase` rows:
- Duplicate refund issued — 2+ `Refund` transactions, same `(propertyId, agent)`.
- After-hours rate override — `Rate override` transaction posted outside 06:00–23:00.
- Cash variance at close — `Cash close` transaction with `abs(amount) > 500`.
- Discount above threshold — `Discount` transaction with `abs(amount) > 1300`.

Each rule's boolean condition alone gates whether a case is created; a derived `confidence` score (rule-specific base + an amount-scaled bonus, clamped 1–99) only decides display severity (`>=90` CRITICAL / `>=75` HIGH / else MEDIUM) — never a second filter that could silently drop a real match. This is genuinely rule-based arithmetic, not ML — matches how the project's own Wave 3 notes always described this first step.

`FraudCase.source` (`SEEDED`/`DETECTED`, see the schema note above) lets the rule engine's real detections coexist with the 6 hand-authored illustrative seed rows. `ai-service/app/db.py`'s `replace_detected_fraud_cases()` deletes every `source='DETECTED'` row and reinserts fresh ones on each run, inside one transaction — mirrors `seed.mjs`'s own delete-then-recreate idempotency convention exactly; `SEEDED` rows are never touched. Verified idempotent 2026-08-05: re-running the job with no new transactions left the `DETECTED` count unchanged (4, not 8).

**Zero changes were needed in `aura-next/`** — `FraudCase` already backed the Fraud Detection screen and the Dashboard's Active Fraud Alerts card through the existing property-scoped `/api/fraud-cases`/`/api/dashboard` routes, so newly-inserted `DETECTED` rows (which carry the real `propertyId` of their source `Transaction`) just appear automatically, RBAC and all. Verified in-browser 2026-08-05: CFO's Fraud Detection "Open Cases" went 6→10 (`$28,771` "Amount at Risk"), and the Bayside-scoped GM correctly sees only the 5 Bayside-property cases (1 seeded + 4 detected) among those 10 — same RBAC helpers, no new code path. A "detected vs. seeded" UI badge is a natural next step, not done yet.

**Structure**: `app/db.py` isolates all raw SQL (the one file that'd need to change if the driver is ever swapped later) and handles two Prisma-specific gotchas raw SQL must get right: table/column names need double-quoting (`"Transaction"`, `"propertyId"` — Postgres folds unquoted identifiers to lowercase, but Prisma's are PascalCase/camelCase), and `FraudCase.id`'s `@default(cuid())` is a Prisma-*client*-side generator only, never pushed into Postgres as a DB-level `DEFAULT` — raw inserts must generate their own id (`uuid.uuid4()` is used here; nothing validates cuid format at the DB level). `app/rules.py` is pure arithmetic, zero IO, unit-tested in `tests/test_rules.py` (pytest). `app/jobs/fraud_scan.py` wires `db` + `rules` together and is the single entry point both the CLI and the FastAPI route call — no logic duplicated between the two invocation paths. `app/main.py` is a small FastAPI app: `GET /health`, `POST /jobs/fraud-scan`.

**Run it:**
- One-off scan: from `ai-service/`, `.venv\Scripts\python.exe -m app.jobs.fraud_scan` (prints a summary of cases detected by pattern).
- As a service: `uvicorn app.main:app --app-dir ai-service --port 8001` — or via this repo's `.claude/launch.json` `ai-service` entry (the browser-preview tool's `preview_start`). Port 8001, not 8000 — 8000 was already occupied by an unrelated local service on the dev machine when this was built; adjust if that's no longer true on a given machine.
- Setup: `py -m venv .venv` inside `ai-service/`, then `.venv\Scripts\python.exe -m pip install -r requirements.txt`, then copy `DATABASE_URL` from `aura-next/.env.local` into a new `ai-service/.env` (gitignored — mirrors `aura-next`'s own `.env.local`/`.env.example` split, see `ai-service/.env.example`).
- No Celery/scheduler yet — this stays a manually/HTTP-triggered job, matching the project's already-documented "Celery not built yet" status (see "Known simplifications").

## Known simplifications (things that look real but aren't full pipelines yet)

- **`DashboardSnapshot`'s "Portfolio Revenue" card** is still a single seeded row, not a live aggregate over `Transaction`. Reason: the 32 sample transactions in this dev DB are a small illustrative slice ("tonight's postings"), not a full ledger — summing them would produce a number (in the tens of thousands) unrelated to the portfolio-scale figure ($4.82M) the mock always showed. In the target architecture this KPI is meant to come from ClickHouse (OLAP), not be computed live from Postgres OLTP data, so a snapshot row is the architecturally honest stand-in until that layer exists. The user explicitly chose (2026-08-04) to leave just this one card seeded when the other 3 became live — see below.
- **Dashboard's "Revenue vs. Recovered Leakage" chart** is real seeded data as of 2026-08-03 (`WeeklyFinancials`), no longer the original hand-drawn illustrative SVG, and property-scoped as of 2026-08-05 — but it's still seeded-not-live, same "no OLAP layer yet" rationale as `DashboardSnapshot` below. Not derived from `Transaction`/`LeakageCategory` — there's no real weekly close process feeding it yet. Per-property rows are a proportional split of the old portfolio baseline (by revenue share), not real per-property source data — see the seeding note in "Backend".
- **Fraud Detection's "Model Precision" (94.6%)** is still a hardcoded display value — there's no actual model, so there's nothing to compute precision from.
- **"Open Cases" / "Amount at Risk" on Fraud Detection** count only `OPEN`+`INVESTIGATING` `FraudCase` rows (real data, now status-aware since the 2026-08-01 write-ops change) — still not the same as the Dashboard's unrelated seeded `activeFraudAlerts`/`activeFraudAlertsCritical` snapshot figures, which remain a fixed mock number per the `DashboardSnapshot` note above.
- **Dark mode (the Header's Theme button) is still purely decorative — deliberately, not an oversight.** Every color in this app is a hardcoded light-mode value: the `@theme` tokens in `globals.css` are static hex/rgba, and the "liquid glass" surfaces (`.glass-card` etc.) plus dozens of inline `style={{ background: 'rgba(...)' }}` calls across every screen have no dark counterpart. Neither `AURA.dc.html` (the definitive design spec) nor the `docs/design-reference/` images define a dark theme, so building one means *designing* it first (a full dark token set + re-verifying every glass gradient/shadow reads correctly on a dark background), not just wiring a toggle. Explicitly deferred rather than done as a shallow CSS-filter hack.

## aura-next structure

- `src/app/page.js` — server component, just renders `AuraApp`.
- `src/components/AuraApp.jsx` — `'use client'`, owns all state: `user` (from session, null = logged out), `checkingSession`, `screen`, `collapsed` (sidebar), `mobileNavOpen`, `properties` (the caller's accessible list, fetched from `/api/properties` once `user` is set), `activePropertyId` (null = no filter, i.e. "All Properties"). Checks `GET /api/auth/me` on mount. Passes `properties`/`activePropertyId`/`onPropertyChange` (=`setActivePropertyId`) to both `Header` and the current `Screen`, and `onNavigate` (=`setScreen`) to `Header` — this is the single source of truth the property switcher, the Transactions property pill, and Header search-result clicks all read from and write to, so changing it from any one of those surfaces stays in sync everywhere else.
- `src/app/api/**/route.js` — Route Handlers, see "Backend" above. Dynamic segments (`alerts/[id]`, `fraud-cases/[id]`, `night-audit/checklist/[id]`) use Next 16's promise-based `params` — `export async function PATCH(request, { params }) { const { id } = await params; ... }`, not the pre-v15 synchronous shape.
- `src/lib/db.js` — Prisma client singleton (with Neon adapter). `src/lib/session.js` — JWT session cookie helpers (Route Handler-only, uses `next/headers`). `src/lib/jwt.js` — the `next/headers`-free bits (`SESSION_COOKIE_NAME`, `getSessionSecretKey()`) factored out of `session.js` so `src/proxy.js` can verify the same cookie without importing a Route Handler-only API. `src/lib/rateLimit.js` — in-memory login-attempt tracking (`isRateLimited`/`recordFailure`/`clearRateLimit`), used by `auth/login`. `src/lib/format.js` — shared display-formatting helpers, see "Backend" above. `src/lib/access.js` — `getAccessiblePropertyIds()` + `resolvePropertyIds()`, see "Property-level RBAC" above. `src/lib/serializers.js` — shared route response-shaping (`serializeFraudCase`, `serializeAlert`, `serializeNightAuditRun`). `src/lib/data.js` — `navList`/`titles` only.
- `src/proxy.js` — Next.js 16's Proxy convention (renamed from Middleware, see "Known gotchas"). Gates every `/api/*` route except `/api/auth/*` behind a valid session cookie (verified via `src/lib/jwt.js` + `jose`), returning a bare `401` before the route handler even runs. This is defense-in-depth on top of, not instead of, each route's own `getSession()` check.
- `src/app/globals.css` — Tailwind v4 config-in-CSS. `@theme` block defines design tokens (see below). `@layer components` defines reusable classes: `.glass-card`, `.glass-panel`, `.glass-header`, `.glass-login`, `.soft-input`/`.soft-input-plain`, `.btn-primary`, `.btn-ghost`, `.btn-outline`, `.icon-btn`, `.pill`, `.nav-item`/`.nav-item-active`, `.table-scroll`/`.table-min`.
- `src/components/Icon.jsx` — one SVG icon component, switched by `name` prop. No external icon library.
- `src/components/Background.jsx`, `LoginScreen.jsx`, `Sidebar.jsx`, `ScreenHeader.jsx` — layout chrome.
- `src/components/Header.jsx` — takes `user`/`onLogout`/`onMenuClick`/`properties`/`activePropertyId`/`onPropertyChange`/`onNavigate`. Composed of three real (not decorative) sub-components defined in the same file: `PropertySwitcher` (dropdown over `properties`, click-outside-to-close via the local `useClickOutside` hook), `SearchBox` (debounced 250ms fetch to `/api/search`, results dropdown, calls `onNavigate` on a result click), `NotificationsBell` (fetches `/api/alerts?limit=20` once on mount, pulsing dot only when there's an `OPEN` one, "View all" calls `onNavigate('alerts')`). The Theme button stays a plain unwired `<button>` — see "Known simplifications" for why.
- `src/components/screens/*.jsx` — all 9 are `'use client'` and `fetch()` their own API route in a `useEffect`, with a `Loading…` / error-message fallback while `data === null`. Dashboard/Employees/FraudDetection/AlertsCenter/NightAudit (AlertsCenter/NightAudit added 2026-08-03) accept an `activePropertyId` prop and refetch when it changes; Transactions additionally accepts `properties`/`onPropertyChange` for its own property pill (kept in sync with the Header switcher through the shared `AuraApp` state, not a separate local filter) plus local state for its type pill, flagged-only toggle, and debounced search box, all passed as query params to `/api/transactions`. Settings holds its own `tab` state (`Profile`/`Security & Access`/`Notifications`/`Detection Rules`/`Integrations`/`Data & Privacy`) instead of a hardcoded active tab; Security & Access now also has a real password-change form (current/new/confirm, `PATCH /api/user/password`) below the two-factor toggle.
- **Resetting fetched state when a prop like `activePropertyId` changes:** don't reset inside the fetch `useEffect` with a bare `setX(null)` at the top of the effect body — that trips `react-hooks/set-state-in-effect` (calling setState synchronously in an effect). The pattern used here instead (see `Dashboard`/`Employees`/`FraudDetection`) is React's documented "adjust state during render" recipe: track a `loadedFor` state seeded from the prop, and if `loadedFor !== prop` during render, call both setters directly in the render body (not in an effect) to reset the "loaded" flag and clear stale data before the effect's fetch runs.
- `prisma/schema.prisma`, `prisma/seed.mjs`, `prisma.config.ts` — see "Backend" above.

### Design tokens (in `globals.css` `@theme`)
Colors: `ink`, `ink-soft`, `body`, `muted`, `faint`, `faint-2`, `hairline` (grayscale text), `brand`/`brand-light`/`brand-dark`, `teal` (accent), `critical`/`critical-bg`, `warning`/`warning-bg`, `success`/`success-bg`, `info`/`info-bg` (status colors + their translucent backgrounds — these exact bg alpha values vary by usage, don't assume one token fits every case, check `src/lib/format.js`'s `*_META` objects for the exact value used in each context).

## Known gotchas

- **Prisma 7 driver adapters + `prisma generate` after schema changes** — see "Backend" above, this has bitten every schema migration so far.
- **Neon free-tier cold start** — expect the first DB command after idle time to fail once (P1001/P1017) and succeed on retry.
- **Adding a required column to a non-empty table** — use `--create-only` + hand-edited backfill migration, not `migrate reset` (destructive, and blocked by the permission classifier anyway). See "Backend" above.
- **Tailwind v4 + `backdrop-filter`:** never hand-write `-webkit-backdrop-filter` next to a plain `backdrop-filter` in `@layer components` — Lightning CSS (Tailwind v4's compiler) silently drops the unprefixed standard property when both are present, breaking the frosted-glass effect everywhere. Write only the unprefixed property and let Lightning CSS auto-prefix.
- **Next.js 16 is unusually new** (post-training-data). If App Router conventions ever seem to behave unexpectedly, check `aura-next/node_modules/next/dist/docs/` before assuming — `aura-next/AGENTS.md` flags this explicitly. Same caution applies to Prisma 7.
- **Next.js 16 renamed Middleware to Proxy** — the file is `proxy.js` (exporting a `proxy` function + `config.matcher`), not `middleware.js`/`export function middleware`. Same mechanism, new name/file. See `aura-next/node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md` and `src/proxy.js`. Training data / muscle memory will reach for `middleware.js` first — it silently won't run.
- Forcing a Tailwind utility to win over a JS-computed inline `style` (e.g. the sidebar's collapsed-width) requires the `!` important prefix (`max-[860px]:!w-[250px]`) — plain utility classes lose to inline styles.
- **ESLint's `react-hooks/set-state-in-effect` fails the build on a bare `setX(...)` at the top of a `useEffect` body** (e.g. resetting a list to `null` before refetching on a prop change) — it does not matter that the reset is harmless in practice, the rule is purely structural. Fix by either (a) doing the reset in an `async function` inside the effect so the `setState` call happens after an `await`, or (b) for state that must reset in response to a *prop* changing, use React's "adjust state during render" pattern instead of an effect at all — see the `loadedFor` pattern in `Dashboard`/`Employees`/`FraudDetection` (aura-next structure, above). Bit every screen that fetches on a filter-prop change during the 2026-08-01 wiring pass.
- The seeded dev password (`aura-secure-2026`) is plaintext-obvious and fine for local dev only — don't ship it as-is to anything resembling production.
- Login/Settings-name fields are controlled inputs now (real state + real requests); Settings' email/role/default-property fields are intentionally read-only (no edit flow for those yet).
